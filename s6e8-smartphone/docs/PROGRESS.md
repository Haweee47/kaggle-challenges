## 3. 01단계 — EDA

### 3-1. 스크린타임 3형제가 압도적

효과크기 = (중독 평균 − 비중독 평균) ÷ 표준편차. 단위가 다른 변수를 공정하게 비교한다.

| 변수 | 타깃 상관 | 효과크기 | 비중독 → 중독 평균 |
|---|---|---|---|
| `daily_screen_time_hours` | **0.611** | **1.35** | 5.04h → 8.71h |
| `weekend_screen_time` | **0.590** | **1.30** | 6.85h → 10.56h |
| `social_media_hours` | **0.532** | **1.17** | 1.38h → 2.92h |
| `work_study_hours` | 0.251 | 0.55 | 1.87h → 2.57h |
| `gaming_hours` | 0.205 | 0.45 | 1.16h → 1.58h |
| `app_opens_per_day` | 0.064 | 0.14 | 97.9 → 104.6 |
| `sleep_hours` | 0.043 | 0.09 | 6.72h → 6.84h |
| `notifications_per_day` | −0.012 | −0.03 | 147.1 → 145.4 |
| `age` | 0.004 | 0.01 | 26.58 → 26.63 |

> **핵심 인사이트**: 알림 개수와 앱 실행 횟수는 중독과 **무관**하다.
> "얼마나 자주 켜느냐"가 아니라 **"얼마나 오래 쓰느냐"** 가 중독을 가른다.

### 3-2. 결측치가 최대 난관

- 전 열 **4.18% ~ 19.38%** 결측
- 결측이 하나도 없는 완전한 행은 **38.9%뿐** → `dropna()`는 데이터 61%를 버린다
- train/test 결측률 차이가 작아 동일 전처리 적용 가능

### 3-3. 범주형은 신호가 거의 없음

`gender` 2.2%p · `stress_level` 0.6%p · `academic_work_impact` 0.3%p (중독률 편차)

### 3-4. 다중공선성

`daily_screen_time_hours` ↔ `weekend_screen_time` 상관 **0.80**
→ 비율·차이 파생변수를 만들 여지 (04단계에서 검증 → **효과 없었음**)

## 4. 02단계 — 전처리 방침

| 항목 | 결정 | 근거 |
|---|---|---|
| 결측치 | 원본 유지 우선 | 중앙값 대치 시 인위적 봉우리로 분포 왜곡 |
| 인코딩 | `category` dtype | 열이 늘지 않고 크기 순서 오해도 없음 |
| 스케일링 | **하지 않음** | 트리 모델은 값의 *순서*만 사용 |
| 검증 | `StratifiedKFold(5, shuffle=True, random_state=42)` | 불균형 데이터 + 재현성 |

### 구조적으로 막아둔 함정 2가지

**1. 데이터 누수** — 대치값을 전체 데이터에서 계산하면 검증 폴드 정보가 학습에 샌다.
`impute_median()`이 계산한 중앙값을 **반환**하도록 설계해, 학습 폴드에서만 계산하고
검증·테스트에는 *적용만* 하도록 강제했다.

**2. 카테고리 순서 불일치** — train/test에서 각각 `astype('category')`를 하면
`Male`이 한쪽에선 1번, 다른 쪽에선 0번이 될 수 있다. 눈에 안 띄면서 점수만 갉아먹는 버그라
`align_categories()`로 카테고리 목록을 합집합으로 통일했다.

## 5. 03단계 — 베이스라인 (CV 0.963574)

| 항목 | 값 |
|---|---|
| 폴드 평균 ± 표준편차 | 0.963576 ± 0.000562 |
| 사용 피처 | 12개 (원본) |
| 평균 트리 개수 | 1,761 |
| 학습 시간 | 194.6초 (5-Fold) |

### 결측 처리 4전략 실측 (탐색용 고속 설정)

| 전략 | CV AUC | 베이스라인 대비 |
|---|---|---|
| **D. 원본 + 행별 결측 개수** | **0.963299** | **+0.000549** |
| C. 원본 + 결측 표시 변수 12개 | 0.962897 | +0.000148 |
| A. 원본 유지 | 0.962750 | 기준 |
| B. 중앙값 / 최빈값 대치 | 0.962478 | −0.000272 |

### ⚠️ 가설이 빗나간 지점 ① — 결측 정보는 쓸모가 있었다

01단계에서 *"결측 여부와 타깃의 관계가 최대 0.42%p이므로 결측 표시 변수는 쓸모없을 것"*
이라 예측했다. **실측은 반대였다. C와 D 모두 베이스라인보다 높았다.**

**왜 빗나갔나**

1. **상호작용(interaction)** — EDA에서 본 것은 "한 변수의 결측 여부"와 타깃의 1:1 관계다.
   트리 모델은 *"스크린타임이 8시간이면서 결측이 3개인 사람"* 같은 **변수 간 조합**을
   자동으로 찾아낸다. 단변량 상관분석으로는 절대 보이지 않는다.
2. **요약이 개별보다 나았다** — 개별 표시 변수 12개(C)보다 하나로 합친 `n_missing`(D)이
   더 좋았다. 열을 12개 늘리면 정보는 희석되고 노이즈만 늘어난다.

> **교훈**: EDA는 **가설을 만드는 단계**지 결론을 내는 단계가 아니다. 최종 판단은 항상 CV다.
> 단, 개선폭 +0.0005는 폴드 표준편차(0.00056)와 비슷하다. "확실한 개선"보다
> **"약한 신호"** 로 보는 것이 정직하다.

### 6-1. 애블레이션 — 그룹별 단독 효과

원본 12피처에 그룹을 **하나씩만** 추가해 순수 효과를 분리 측정.

| 그룹 | 추가 변수 | CV AUC | 대비 |
|---|---|---|---|
| **구성비율** | `social_ratio`, `gaming_ratio`, `study_ratio` | **0.963426** | **+0.000676** |
| *(전체 12개)* | 모든 파생변수 | 0.963167 | +0.000417 |
| 여가지표 | `leisure_hours`, `leisure_vs_study` | 0.963091 | +0.000341 |
| 사용강도 | `mins_per_open`, `opens_per_notif` | 0.962869 | +0.000119 |
| 주말패턴 | `weekend_ratio`, `weekend_diff` | 0.962859 | +0.000109 |
| 시간예산 | `awake_hours`, `screen_per_awake`, `sleep_screen_sum` | 0.962734 | −0.000016 |

### 6-2. 조합 실험 — 피처를 늘릴수록 나빠진다

| 조합 | 피처 수 | CV AUC | 대비 |
|---|---|---|---|
| **K1. 원본 + `n_missing` + 구성비율** | **16** | **0.963546** | **+0.000796** |
| K2. K1 + 여가지표 | 18 | 0.963537 | +0.000787 |
| K3. K2 + 주말패턴 | 20 | 0.963031 | +0.000281 |
| K4. K3 + 사용강도 | 22 | 0.963024 | +0.000274 |
| K0. 베이스라인 | 12 | 0.962750 | 기준 |

**16피처가 최적점.** 이후로는 단조 감소한다.

**왜 쓸모없는 피처가 점수를 깎는가** — LightGBM은 트리를 만들 때마다 모든 후보 변수를
검토해 최적 분기를 찾는다. 기여도 낮은 변수가 섞이면 ① 그 변수로 분기하는 트리가 우연히
만들어지고(노이즈 학습), ② `feature_fraction=0.8` 때문에 정작 좋은 변수가 후보에서
빠지는 일이 잦아진다. **쓸모없는 피처는 중립이 아니라 마이너스다.**

### 6-3. 최종 피처셋 (16개)

```python
원본 12개
  + n_missing      # 행별 결측 개수
  + social_ratio   # social_media_hours / daily_screen_time_hours
  + gaming_ratio   # gaming_hours       / daily_screen_time_hours
  + study_ratio    # work_study_hours   / daily_screen_time_hours
```

`src/preprocess.py`의 `build_final()`로 고정 → 05단계에서 동일하게 재현.

### 6-4. Optuna 튜닝 (12회 탐색, 542초)

| 파라미터 | 기본값 | 탐색 결과 | 의미 |
|---|---|---|---|
| **`lambda_l1`** | ≈0 | **4.906** | L1 규제 대폭 강화 |
| **`feature_fraction`** | 0.80 | **0.533** | 트리당 변수 사용 축소 |
| `num_leaves` | 63 | 84 | 트리 복잡도 증가 |
| `bagging_fraction` | 0.80 | 0.974 | 행은 거의 전부 사용 |
| `min_child_samples` | 50 | 42 | 거의 변화 없음 |
| `lambda_l2` | ≈0 | 0.189 | 소폭 강화 |

### ⚠️ 가설이 빗나간 지점 ② — "피처가 튜닝보다 중요하다"가 안 맞았다

**튜닝(+0.000565)이 피처 엔지니어링(+0.000378)보다 기여가 컸다.** 통념과 반대다.

- **원본 신호가 이미 매우 강하다** — 단일 변수 상관 0.611, 베이스라인 AUC 0.9636.
  짜낼 정보가 별로 안 남아 파생변수가 보탤 여지가 작았다.
  실제로 파생변수 3개의 gain 비중은 **11.01%** 에 그쳤다.
- **규제가 결정적이었다** — 유효 변수가 적은 상황에서는 불필요한 분기를 억제하는
  L1 규제와 낮은 `feature_fraction`이 큰 힘을 발휘한다.
- **피처 탐색 공간이 좁았다** — 파생변수를 12개만 만들어봤다.

> **일반화하지 말고 측정하라.** "무엇이 더 중요한가"는 데이터마다 다르다.

## 7. 05단계 — 앙상블 (CV 0.964890)

### 7-1. 개별 모델 vs 앙상블

| 구분 | 방법 | CV AUC | 최고 단일 대비 | 학습 시간 |
|---|---|---|---|---|
| 단일 | XGBoost | 0.964521 | 기준 | 487초 |
| 단일 | LightGBM | 0.964516 | −0.000005 | **225초** |
| 단일 | CatBoost | 0.963579 | −0.000942 | **3,978초** |
| 앙상블 | 가중 평균 (0.40/0.45/0.15) | 0.964951 | +0.000431 | — |
| 앙상블 | **단순 평균 (채택)** | **0.964890** | **+0.000369** | — |
| 앙상블 | 순위 평균 | 0.964889 | +0.000369 | — |

모델 간 OOF 상관: **0.99289**

### 7-2. 실측으로 확인한 4가지

**1. 상관 0.99 초과여도 앙상블은 이득을 준다**
통상 기준표대로면 "이득이 거의 없어야" 했지만 **+0.000369**를 얻었다.
04단계 피처 엔지니어링의 이득(+0.000378)과 맞먹는다.

이유: **AUC는 예측값의 절대 크기가 아니라 순서로 계산된다.** 상관 0.993은 전체적으로
비슷하게 예측한다는 뜻이지, **경계에 걸친 애매한 샘플들의 순서까지 같다는 뜻은 아니다.**
AUC를 가르는 것은 바로 그 애매한 구간이다.

**2. 단순 평균이 사실상 최선이다**
가중 평균이 +0.000061 더 높았지만 그 가중치는 OOF에서 찾은 값이라 **OOF에 과적합**돼 있다.
차이가 폴드 표준편차(≈0.0005)의 1/8이라 리더보드에서 뒤집힐 수 있다.
→ 노트북이 자동으로 **단순 평균**을 채택하도록 규칙을 넣어뒀다.

**3. 가장 느린 모델이 가장 약했다 — 비용을 측정하라**
CatBoost는 **3,978초(약 66분)** 로 LightGBM의 **18배** 시간을 쓰고도 CV가 가장 낮았다.
최적 가중치 0.15를 받았으니 다양성 기여는 있었지만 **투자 대비 수익은 명백히 나쁘다.**
시간이 제한적이라면 그 시간에 LightGBM을 다른 시드로 여러 번 돌리는 편이 나았다.

> 캐글에서는 점수만이 아니라 **점수/시간**을 봐야 한다.

**4. 개선의 크기를 정직하게 보자**
전체 여정의 개선은 **+0.001316**이다. AUC가 이미 0.96대라 여지가 좁았고,
각 단계 이득은 폴드 표준편차와 비슷한 규모였다.

## 7-3. CV vs LB — 검증 틀은 믿을 만한가

| 지표 | 값 |
|---|---|
| CV AUC (OOF) | 0.964890 |
| **Public LB** | **0.96613** |
| 차이 (LB − CV) | **+0.00124** |

### LB가 CV보다 높다 — 이건 좋은 신호다

과적합이 있었다면 **LB가 CV보다 낮게** 나온다. 반대 방향이므로 검증 틀이 건전하다.
게다가 이 방향은 **구조적으로 예상되는 결과**다.

**이유 1 — 테스트 예측은 5개 모델의 평균이다**

| | 무엇으로 예측했나 | 효과 |
|---|---|---|
| OOF (CV용) | 폴드마다 **단일 모델** 하나 | 그 모델의 분산이 그대로 반영됨 |
| 테스트 예측 | **5개 폴드 모델의 평균** | 분산이 줄어 예측이 더 안정적 |

즉 CV 점수는 "단일 모델의 실력"이고, LB 점수는 "5개 모델을 앙상블한 실력"이다.
**애초에 LB 쪽이 조금 유리한 비교**다. 여기에 3개 알고리즘 블렌딩까지 더해지니
실질적으로는 15개 모델의 평균이 제출된 셈이다.

**이유 2 — Public LB는 테스트셋의 일부만 채점한다**

Public 점수는 test 296,302행 중 일부로만 계산된다. 표본이 작을수록
운에 따라 흔들리므로 ±0.001 정도의 차이는 노이즈 범위다.
**최종 순위는 나머지로 계산되는 Private LB로 정해진다.**

### 결론 — CV를 계속 신뢰해도 된다

- 차이가 +0.00124로 작고 방향도 유리하다 → **누수(leakage)나 과적합 징후 없음**
- 앞으로도 **CV를 기준으로 실험을 판단**하면 된다

### ⚠️ 단, 아직 확인 못 한 것

**점 하나로는 CV-LB "상관"을 말할 수 없다.** 지금은 v3만 제출했다.
`submission_v1_baseline.csv`(CV 0.963574)와 `submission_v2_tuned.csv`(CV 0.964516)도
제출해서 **세 점이 같은 방향으로 움직이는지** 봐야 검증 틀을 제대로 검증한 것이다.

| 제출 | CV | LB | 확인 |
|---|---|---|---|
| v1 베이스라인 | 0.963574 | *미제출* | — |
| v2 FE + 튜닝 | 0.964516 | *미제출* | — |
| v3 앙상블 | 0.964890 | **0.96613** | ✅ |

세 점의 CV 간격은 각각 +0.00094, +0.00037로 매우 좁다.
**LB에서 순서가 뒤집힐 가능성도 충분하며, 그것 자체가 중요한 정보다.**
